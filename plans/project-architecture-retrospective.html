Fantasy Draft Assistant / What Was Actually Built

From draft-day idea to a local decision system.

This is the implementation record behind the project: the runtime architecture, offline data pipeline, recommendation design, major tradeoffs, plan changes, validation results, and lessons learned while turning first-pass.html into a working application.

The finished shape

One canonical Sleeper sync service feeds both clients. Cached current-season data and offline model outputs are merged in the React app, where a transparent recommendation layer adds roster need, scarcity, draft stage, and next-pick timing.

The core thesis

Prediction answers "how good is the player?" Recommendation answers "how valuable is the player to this roster at this pick?" Keeping those questions separate became the most important architectural decision.

Local Sync Server

A lightweight Node HTTP service owns the canonical Sleeper draft snapshot instead of asking each client to interpret the draft independently.

  • Polls draft metadata and picks in parallel every second.
  • Stores one in-memory session per draft ID.
  • Streams the same normalized snapshot to the app and extension.

Plan vs Reality

What changed after the first pass

The original plan established the prediction direction. Implementation sharpened source ownership, added a canonical sync boundary, and introduced guardrails where real draft behavior exposed weaknesses in a pure score-first design.

Area First-pass direction What was implemented Why it changed or held Status
Runtime storage JSON for the app, DuckDB for modeling. Exactly that boundary: generated JSON enters the browser; DuckDB stays offline. It preserved a zero-ops local runtime while allowing serious analytical joins. Held
Prediction vs recommendation Train player-quality signals separately from roster decisions. predictions.json supplies quality; runtime calculations add need, scarcity, survival, and stage. Roster context is transient and should not contaminate player-quality labels. Held
Sleeper synchronization The initial product had direct app polling and extension DOM detection. A local sync server and shared DraftSyncEngine became the canonical source. Two overlapping clients could not reconcile independently or expose reliable sync health. Expanded
Transport WebSocket-style shared event types were anticipated. HTTP snapshots plus Server-Sent Events are used for server-to-client updates. The data flow is mostly one-way; SSE is smaller and easier than full duplex sockets. Simplified
Market data Compare FantasyPros ECR with Sleeper ADP. Sleeper is labeled search_rank / market proxy, not observed-draft ADP. The original label overstated precision and source semantics. Corrected
Team environment Use offensive environment as a player feature. Replaced hand-maintained ratings with a reproducible nflverse-derived generator. Manual rankings drift, hide assumptions, and cannot be backtested cleanly. Upgraded
League history Use historical drafts to improve recommendations. League data is restricted to next-pick survival and room tendencies. A small home-league sample can inform timing, but not general player quality. Narrowed
Recommendation score Weighted expert, market, projection, environment, need, urgency, and risk. Transparent sub-scores plus stage-aware special-teams and duplicate-position guardrails. Raw VOR and rank arithmetic produced plausible but strategically poor edge cases. Hardened
Model validation Backtest before claiming improvement. A transparent replay baseline was built; it underperformed ECR-only in its first form. The result was kept as evidence, not hidden. It prevents unsupported product claims. Provisional

Design Record

The decisions that shaped the project

Filter by concern. Each choice is tied to a concrete failure mode or operating constraint discovered during implementation.

Sync01

Make one service the system of record

Web app polling and extension scraping were useful prototypes, but they created two truths. The local server now owns reconciliation and health.

Sync02

Prefer official API data over DOM observations

Sleeper API picks are marked confirmed. DOM detection remains a context and fallback mechanism because page markup is less stable.

Sync03

Use SSE for a one-way update problem

The clients mainly receive state. HTTP plus SSE avoids extra protocol complexity while preserving live updates and straightforward testing.

Data04

Give every source one explicit job

FantasyPros owns current expert context, Sleeper owns platform state, nflverse owns history, and league drafts own room timing.

Data05

Cache before draft time

The live decision loop reads local artifacts. It does not depend on network-heavy ranking, projection, or model refreshes while the clock is running.

Data06

Treat matching as a data product

ID maps are preferred; normalized name, position, and team fallbacks are guarded against duplicates to avoid confidently joining the wrong player.

Model07

Separate quality from choice

Projected output and uncertainty belong to prediction. Roster gaps, scarcity, current pick, and survival belong to recommendation.

Model08

Use league history for timing, not truth

Four seasons and 550 modeled rows are enough to describe room tendencies, but too small and biased to train universal player outcomes.

Model09

Keep the scorer inspectable

Recommendation diagnostics expose expert, market, projection, VOR, urgency, risk, uncertainty, need, and scarcity contributions.

UI10

Design around the current pick

The on-the-clock panel answers the immediate question first. Full rankings, best value, needs, and diagnostics support that decision instead of competing with it.

UI11

Show confidence and source freshness

A recommendation without data age, source type, and model provenance looks more certain than it is. The interface now surfaces that context.

Operations12

Never refresh data implicitly during dev

pnpm dev checks freshness but does not rewrite tracked artifacts or make hidden network requests. Refreshes are explicit and reproducible.

Guardrail

Draft stage can override a mathematically attractive score

Kicker and defense receive a large early-draft penalty. Second QB and TE VOR are reduced when those positions are only depth. These rules were added after raw replacement value produced strategically bad recommendations.

Interpretation

"Best player" and "best pick" remain separate lists

Best Available isolates composite player quality. Draft Now adds roster and timing. Best Value only shows market discounts that are still above replacement, while lower-value discounts are moved into a separate stash view.

Build Learnings

What the project taught us

These are the durable engineering and product lessons that came from implementing and testing the system, not assumptions copied from the original plan.

01

Canonical state is more valuable than another feature

Once both clients consumed the same normalized snapshot, sync health, retries, confidence, and tests became tractable.

02

Source labels are part of correctness

Calling search_rank "ADP" made the product sound more precise than the source. Naming the proxy accurately changed how it was weighted and explained.

03

Prediction quality does not decide a draft pick alone

The current roster, remaining tiers, pick distance, and draft stage can rationally reverse the order of two similarly projected players.

04

Small personal datasets are useful when scoped tightly

Four league seasons are informative for positional timing. They are not a defensible foundation for universal player-outcome prediction.

05

Transparent failure beats an impressive claim

The first replay model lost to ECR-only. Keeping that result exposed missing roster, injury-date, keeper, and room-state features that need better validation.

06

Heuristic systems need explicit strategic guardrails

A score can be internally consistent and still recommend an early kicker or redundant quarterback. Draft-stage rules encode constraints the base arithmetic misses.

07

Offline complexity can produce a simple runtime

DuckDB performs the expensive joins and modeling, then emits compact JSON. The browser remains fast, inspectable, and independent of database availability.

08

Freshness is a product feature

Cached data makes the draft resilient, but only if the user can see its age and knows when to refresh it. Hidden staleness is worse than an explicit fallback.

09

Browser extensions have lifecycle edge cases

Reloading an extension does not reliably reinject content scripts into open Sleeper tabs. The operational workflow must explicitly include refreshing the draft page.

-613.94

Transparent Model V1 captured less VOR than the ECR-only replay

The baseline replay captured 863.66 VOR versus 1477.60 for ECR-only across 49 evaluated picks. This does not invalidate the architecture; it shows the current historical replay is incomplete and should not be marketed as proven.
