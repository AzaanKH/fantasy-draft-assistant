# Existing draft-session persistence defects

These defects occur at unit 11a's assigned base, `75e8def`. Unit 11a leaves production behavior unchanged. Unit 11c owns the fixes. The reusable browser check is described in [the persistence runner](../../scripts/persistence/README.md). The operator's full raw results and screenshots are under the untracked `artifacts/agent-friendly-plan/units/u11a/` directory.

## Completed characterization

The four-scenario Chromium 148 matrix submits 36,000 commands, 9,000 per scenario. Each scenario repeats five seeds three times, with two actors issuing 300 commands. All stress commands are acknowledged. Every completed shared-storage run has the same missing effects before and after reload, and the stored head matches the reloaded state. Captured write errors, uncaught page errors, and scenario errors are zero.

| Scenario | Commands | Kept in tab | Missing from tab | Absent from both reloaded sessions |
| --- | ---: | ---: | ---: | ---: |
| Two top-level tabs | 9,000 | 5,107 | 3,893 | 3,893 |
| Tab + installed extension, host permission | 9,000 | 5,411 | 3,589 | 3,589 |
| Tab + installed extension, no host permission | 9,000 | 4,500 | 4,500 | 0 |
| localhost + 127.0.0.1 | 9,000 | 4,500 | 4,500 | 0 |

The two negative scenarios retain all 9,000 effects across the union of two partitions, with 4,500 in each. The missing-from-tab count represents a split, not effects absent from both sessions. The no-permission probe cannot read the tab marker and has no extension permission-error overlay after 8.5 seconds. The hostname probe also cannot read the peer marker. The two shared-origin sequential controls retain 600 of 600; negative controls retain 300 per partition. Both shared-origin conflicting-pick samples acknowledge both players but reload one.

These rates describe a deliberately dense synthetic contention schedule, not the expected frequency for users. The workload, raw audit recomputation, and future gate are documented in the runner README. The full matrix ran with HMR disabled before final metadata and module-label cleanup. Its requested watch-null override was ignored by Vite 6 config merging, as the later runtime assertion exposed. Production persistence files stayed unchanged throughout; no HMR updates occurred. The committed runner now disables watching in configResolved and verifies the resolved value. The PR reports a separate all-four-scenario smoke on the committed head with final source hashes. The aborted HMR run and the deliberately stopped intermediate run are excluded.

## D1: concurrent writers lose acknowledged effects

Run `pnpm test:persistence` with its default matrix, or select `PERSISTENCE_SCENARIOS=tabs`. Each actor records 150 provisional picks and 150 distinct queue additions. All commands target disjoint slots and IDs. Reload both pages after the actors finish. Compare every accepted pick identity and queue member with both reloaded stores.

The first 600-command smoke run acknowledged all 600 effects and retained 358. The other 242 were absent from both tabs. There were no JavaScript or storage errors. The same commands, run sequentially in the full run's control, retain all 600 effects. The full run records exact missing IDs, raw heads, and per-tab journals before and after reload. Convergence alone is insufficient: both pages can agree on the surviving subset.

A deterministic expected-failure test in `draftStore.persistence.test.ts` covers one cause. Pause a stale writer after its CAS check by intercepting its journal write. Let the other store acknowledge two picks. The stale writer then writes its older head. The picking store has only its latest journal, whose `baseWriteId` points to the first overwritten pick. Recovery cannot resolve that base and removes the journal. Both picks disappear. This establishes a defect in the existing recovery algorithm. The measured smoke and first complete two-tab suite already lack the same effects before reload. Reload does not cause those losses. This does not attribute every browser loss to that exact interleaving, and the loss rate is not a frequency estimate for ordinary draft use.

Fix in 11c by applying the command against the latest facts inside one IndexedDB transaction and acknowledging only on transaction completion. Retain this race as a regression test against the replacement's acknowledgement contract.

## D2: valid orphan journals are deleted

Start a session, save the baseline bytes, and acknowledge two successive picks. Restore the baseline head to simulate a stale overwrite. The newest valid journal depends on a write absent from the surviving head's lineage. Open another store. `takeOverwrittenChanges` removes the unresolved journal instead of retaining it or surfacing a recovery error.

The orphan-journal expected-failure test preserves the exact journal bytes and asserts they remain after recovery. The journal is generated by the real writer, so decoder rejection is not the explanation. The same unresolved dependency can occur when an imported base is rejected. The import wave must preserve valid journals and raw rejected bases, report the dependency, and keep activation blocked until the dependency is resolved.

## D3: failed storage writes still acknowledge a pick

Open a session successfully, then make both journal and head writes throw `QuotaExceededError`. `recordProvisionalPick` returns true and the local store shows the pick. Restore storage and reload before another successful command. The pick is gone.

The quota expected-failure test checks the durable acknowledgement invariant. A replacement may reject the command or persist it, but it must never acknowledge an effect that reload loses. The existing in-memory fallback test stays unchanged. Unit 11c must surface the failed durable save distinctly from a local-only view.

## D4: missing extension host permission creates separate writable sessions

Build the extension normally. Copy its unpacked build and remove only localhost and 127.0.0.1 entries from `host_permissions`. Keep its frame CSP unchanged. Launch it in a fresh Chromium profile with storage partitioning enabled, set only the synthetic pairing fixture, and open `sidepanel.html` plus a normal `/draft` tab.

Both documents load. The marker written in the tab cannot be read by the frame. Both contexts can accept commands for the same draft identity, but each reloads only its own partition. The copied manifest, actual granted permissions, UI overlay state after the eight-second load timeout, and screenshot are retained by the runner. The demo can show quick-mock readiness warnings caused by the stress fixture's larger draft size; those warnings do not identify the missing host permission. The extension error, loading, and pairing overlays are hidden while store commands are accepted. This is a sharing failure, distinct from effects absent from both reloaded sessions. Unit 11c must block frame writes and show the permission or setup error until sharing is proved.

## D5: localhost and 127.0.0.1 split one draft identity

Open `/draft` at `http://localhost:3000` and `http://127.0.0.1:3000` in the same browser profile. Bind the same session identity and issue disjoint commands. Each origin reloads its own history and queue. The tab marker is absent in the peer origin. Those effects still exist in separate stores, but no common session contains them.

Unit 11c must canonicalize the origin before a workspace can write. Redirecting alone cannot import another origin's storage. Export that origin's records before the explicit handoff.

## D6: both conflicting picks can be acknowledged

Bind two same-origin tabs to one draft identity. Issue different provisional players for the same empty slot concurrently. In the first completed two-tab characterization, both `alice` and `bob` returned accepted. Both reloaded stores retained `alice` alone. The runner records both receipts and compares each accepted identity with the final slot. `conflictFailures` and `conflictLostPicks` make this failure visible in the summary and gate.

Unit 11c must serialize the acceptance decision inside the transaction. Exactly one command may acknowledge the slot; the other command must return a rejection. Concurrent queue moves can both be valid when the later move intentionally supersedes the earlier one. Their separate gate requires one common final order, a valid queue permutation, and a final destination requested by an accepted command.
